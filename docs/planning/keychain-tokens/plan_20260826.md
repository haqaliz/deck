From `prd.md` (critique folded in) + `probe.md`. All five open questions are
resolved by user decision; nothing here is left to discover.

## Commands used throughout

```bash
xcodegen generate --spec native/project.yml            # after ANY new file
xcodebuild -project native/Deck.xcodeproj -scheme DeckSharedTests \
  -destination 'platform=macOS' test                    # unit tests
xcodebuild -project native/Deck.xcodeproj -scheme DeckApp -configuration Release \
  -derivedDataPath native/build.noindex -allowProvisioningUpdates \
  -allowProvisioningDeviceRegistration build            # full build
scripts/lsclean.sh                                      # after every release build
```

⚠️ **xcodegen enumerates files at generation time.** A new test file that is not
regenerated in is silently not compiled *and the suite still reports success*.
Every phase that adds a file regenerates first.

## Phase 1 — `DeckKeychain`: the wrapper and its result type (pure-ish, tested)

**Goal:** one place that talks to `SecItem*`, returning a result that can tell
*absent* from *failed* — the distinction the whole feature rests on.

**Files:** `native/Shared/DeckKeychain.swift` (new),
`native/SharedTests/DeckKeychainTests.swift` (new).

**Steps**
1. `enum DeckSecret: String, CaseIterable` — the five accounts:
   `openbox.token`, `shipbox.token`, `taskbox.token`, `prbox.github.token`,
   `prbox.azure.token`. Service is `com.deck.app` for all five.
2. `enum SecretRead: Equatable { case found(String), absent, failed(OSStatus) }`.
3. `read(_:) -> SecretRead`, `write(_:value:) -> OSStatus`,
   `delete(_:) -> OSStatus`. `write` is add-or-update: `SecItemAdd`, and on
   `errSecDuplicateItem` fall through to `SecItemUpdate`.
4. Map `errSecItemNotFound` → `.absent`; every other non-zero status →
   `.failed`. **Never** collapse a failure into `.absent` — that is C1.
5. Legacy keychain only: no `kSecUseDataProtectionKeychain`, no
   `kSecAttrAccessGroup`, **no entitlement anywhere**. See the CLAUDE.md trap.

**Verification (TDD — RED before GREEN)**
- Tests use a distinct service (`com.deck.app.tests`) via an injected service
  string so they never touch the real items; each test deletes what it wrote.
- round-trip: write → read → `.found(value)`; overwrite → `.found(new)`.
- read of an unwritten account → `.absent` (never `.failed`).
- delete → subsequent read `.absent`.
- `DeckSecret.allCases.count == 5` and the raw values are stable (a rename
  would strand a user's stored token).

**Dependencies:** none.

## Phase 2 — Hydrate and scrub on `DeckSettings` (pure, tested)

**Goal:** the two host-side transforms, with the precedence rule from C2 pinned
by a test.

**Files:** `native/Shared/DeckSettings.swift`,
`native/SharedTests/DeckSettingsSecretsTests.swift` (new).

**Steps**
1. `DeckSettings.scrubbedOfSecrets() -> DeckSettings` — a copy with the five
   fields blanked.
2. `save()` encodes `scrubbedOfSecrets()`. **`encode(to:)` is not touched** —
   `DecodeTests` (`:477`, `:504`, `:509`, `:644-646`) must keep passing
   unmodified; they are the tolerant-decode regression pins.
3. `mutating func hydrate(from reads: [DeckSecret: SecretRead]) -> Set<DeckSecret>`
   — pure, takes the reads rather than calling the keychain, so it is testable
   without I/O. Returns the set of keys that `.failed`.
4. **`.found` overwrites; `.absent` and `.failed` leave the decoded value
   exactly as it was** (C2). Hydrate never blanks.
5. A thin `hydrateFromKeychain()` that gathers the five reads and calls (3).

**Verification**
- `save()` writes a file whose five token fields are `""` while the in-memory
  struct still holds them.
- A fully-populated `DeckSettings` round-trips through `scrubbedOfSecrets()`
  equal in every field **except** the five.
- hydrate with `.found` overwrites; with `.absent` **keeps** a pre-existing file
  value (the upgraded-but-never-opened case); with `.failed` keeps it *and*
  reports the key.
- The existing `DecodeTests` suite passes untouched.

**Dependencies:** Phase 1 (for `SecretRead`).

## Phase 3 — The fifth `FetchOutcome`, tolerantly decoded (pure, tested)

**Goal:** a locked keychain can say so, and an older Deck reading a newer status
file does not choke.

**Files:** `native/Shared/FetchStatus.swift`,
`native/SharedTests/FetchStatusTests.swift`.

**Steps**
1. Add `case credentialsUnavailable` to `FetchOutcome`.
2. Tolerant `init(from:)`: an unrecognised rawValue decodes to `.unreachable`
   (C5) — the rule `FetchStatus.swift:140-142` already states for unrecognised
   errors.
3. `FetchStatusCopy.line`: "Can't read saved credentials" for `shipbox`,
   `taskbox`, `opencodeRemote`, `prboxGitHub`, `prboxAzure`; `nil` for
   `weather`, `calbox`, `marketbox` (no credentials — unreachable state).
4. `FetchStatusCopy.hint`: "Deck couldn't read the saved token from your
   keychain — unlock your login keychain and it will retry." for the five;
   `nil` for the three. **`hint` must speak exactly when `line` speaks** — the
   file's own invariant.
5. `outcome(forFailedSecret:) -> FetchOutcome` — the pure mapping C6 asks for.

**Verification**
- Decoding `{"outcome":"somethingNew"}` yields `.unreachable`, not a throw.
- `line`/`hint` are non-nil for exactly the five token-bearing sources and nil
  for the other three, asserted by iterating `FetchSource.allCases`.
- Existing fetch-status tests pass unmodified.

**Dependencies:** none (parallel with 1–2).

## Phase 4 — Agent: hydrate, and gate on failure before "not configured"

**Goal:** the 60s tick reads credentials from the keychain and reports a locked
keychain honestly.

**Files:** `native/DeckAgent/main.swift`.

**Steps**
1. After `DeckSettings.load()` (`:44`), hydrate and keep the failed set.
2. At each of the five gates (`:50` openbox, `:133` shipbox, `:164` taskbox,
   `:214` prbox.github, `:234` prbox.azure) insert **one line ahead of the
   existing check**: if this source's key failed → `FetchStatusStore.record(
   .credentialsUnavailable, for: <source>)` and skip the fetch. The
   `isEmpty`/`isUsable` logic below is untouched (C1).
3. Change nothing else — no cadence change, no snapshot change, no new write.

**Verification**
- Build. With tokens present in the keychain, run the agent by hand and confirm
  `shipbox.json` / `taskbox.json` / `prbox.json` refresh with new timestamps.
- `fetch-*.json` shows `ok` for the configured sources.

**Dependencies:** Phases 1–3.

## Phase 5 — App: hydrate, commit-on-edit, migration, erase

**Goal:** the settings window writes to the keychain, the file loses its
secrets, and existing installs migrate safely.

**Files:** `native/DeckApp/DeckApp.swift`.

**Steps**
1. At launch, beside `tightenPermissions()`: **migrate** — for each of the five,
   if the loaded value is non-empty, `write` → **read back to confirm** → only
   then blank it and `save()`. Any failure leaves the file untouched; the
   migration is idempotent and retries next launch (C4).
2. Then hydrate, keeping the failed set, exactly as the agent does.
3. The five `SecureField`s (`:735`, `:1156`, `:1174`, `:1209`, `:1343`) bind to
   local `@State` and commit to the keychain on submit / focus loss, not on
   every keystroke (user decision). On commit, also refresh the in-memory
   settings value so the refresh pumps and `clearOn` keys still see it.
4. The five host refresh pumps (`:168`, `:255`, `:276`, `:307`, `:335`) get the
   same failed-key gate as the agent.
5. `eraseDeckData` (`:494`) also deletes the five keychain items — best-effort
   and silent, matching its existing `try?` sweep (C7). Its doc comment already
   promises "the saved tokens"; this makes that true again.

**Verification**
- Type a token → quit and reopen Deck → the field still shows a value and
  `grep -c token "…/settings.json"` shows the keys present but **empty**.
- `security find-generic-password -s com.deck.app -a shipbox.token` finds it.
- Erase Deck data → the same command finds nothing.

**Dependencies:** Phases 1–3.

## What stays unverified (say so at merge)

**A locked login keychain.** `security lock-keychain` on the user's own machine
would leave unlock prompts across their other apps that cannot be undone
without their password (`probe.md`). The `credentialsUnavailable` path is
implemented and unit-tested through its pure mapping, but has never been
exercised by a genuinely locked keychain. Do not claim otherwise.
